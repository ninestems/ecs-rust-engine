# Требования к веб-сервису расчёта крафта

## 1. Назначение и границы первой версии

Сервис помогает игроку рассчитывать крафт предметов: разложить рецепт до
базовых компонентов, учесть имеющиеся запасы, собрать несколько целей в одну
«корзину крафта» и оценить затраты. Рецепт может состоять как из базовых
ресурсов, так и из результатов других рецептов.

В первой версии не требуется регистрация обычных пользователей и не требуется
интеграция с игровым клиентом. Данные рецептов и цен хранятся на сервере;
инвентарь и текущая корзина гостя могут храниться локально в браузере.

Грейд предмета (`D`, `C`, `B`, `A`) является частью его игровой
характеристики. В MVP ресурсы разных грейдов не взаимозаменяемы: например,
ресурс грейда `C` не покрывает потребность в таком же ресурсе грейда `D`.

## 2. Роли

### Гость / пользователь

- просматривает каталог и рецепты;
- вносит свой инвентарь;
- строит дерево рецепта;
- считает максимум доступного крафта;
- формирует корзину желаемых крафтов;
- задаёт или использует доступные цены и смотрит стоимость.

### Администратор

- создаёт и изменяет предметы, базовые ресурсы и покупаемые у NPC компоненты;
- создаёт и изменяет рецепты и их ингредиенты;
- задаёт цены предметов и стоимость операций крафта;
- проверяет корректность данных перед публикацией рецепта.

## 3. Функциональные требования

### FR-01. Справочник предметов

Администратор может создать предмет со следующими свойствами:

- внутренний уникальный идентификатор и неизменяемый код;
- отображаемое название;
- грейд `D` / `C` / `B` / `A` (либо отсутствие грейда, если это потребуется
  для особых предметов);
- тип: базовый ресурс, покупаемый компонент, результат крафта;
- необязательная категория для каталога (например, зелья, свитки);
- статус: активен или скрыт из пользовательского каталога.

Название не является ключом расчёта: все связи строятся по `item_id`. Это
исключает ошибки от переименования и похожих названий.

### FR-02. Управление рецептами

Администратор может создать рецепт, указав:

- результат рецепта и количество результата за один крафт;
- список ингредиентов вида «предмет — количество»;
- стоимость одного запуска крафта;
- статус рецепта.

Ингредиентом может быть базовый ресурс, покупаемый у NPC компонент или
результат другого рецепта. Количества результата и ингредиентов должны быть
положительными. Один базовый ресурс не может иметь собственного рецепта.

При сохранении сервер обязан проверить, что все ссылки существуют и что новый
рецепт не образует цикл зависимостей (`A -> B -> C -> A`). Циклический рецепт
не публикуется, потому что его нельзя корректно разложить.

В MVP для одной пары «результат + грейд» допускается один активный рецепт.
Поддержка альтернативных рецептов — отдельное расширение: тогда пользователь
будет выбирать вариант либо сервис будет оптимизировать его по цене.

### FR-03. Дерево выбранного рецепта

Пользователь может выбрать рецепт и количество результата. Сервис показывает
дерево до листьев:

```text
Итоговый предмет × 1
├─ Составной компонент X × 2
│  ├─ Базовый ресурс A × 6
│  └─ Покупаемый у NPC компонент B × 2
└─ Базовый ресурс C × 3
```

Одновременно сервис показывает плоскую сводку: суммарное число каждого
базового и покупаемого компонента, число запусков каждого составного рецепта
и стоимость. Один и тот же компонент, встречающийся в нескольких ветках,
должен быть агрегирован в сводке.

### FR-04. Инвентарь и доступный объём крафта

Пользователь может указать количество любого предмета, в том числе базового
ресурса и уже созданного составного предмета. Для выбранного рецепта сервис
должен определить:

- максимальное целое количество итогового предмета, которое можно создать;
- какие запасы будут израсходованы;
- каких компонентов не хватает для заданного количества;
- как использование готового составного предмета уменьшило потребность в его
  дочерних ингредиентах.

Для расчёта сначала используются подходящие уже имеющиеся составные предметы,
затем недостающее количество раскрывается по их рецептам до базовых или
покупаемых компонентов.

### FR-05. Корзина крафта

Пользователь может добавить в корзину несколько целей: одинаковые или разные
рецепты и количество результата для каждой. Для одной корзины и одного общего
инвентаря сервис возвращает:

- суммарно необходимые базовые и покупаемые компоненты;
- список составных предметов и число запусков каждого рецепта, которые надо
  выполнить;
- предметы из инвентаря, использованные в расчёте;
- дефицит по каждому предмету;
- итоговую стоимость.

Инвентарь не должен расходоваться отдельно на каждую строку корзины: он общий
для всего расчёта. Результат расчёта должен быть детерминированным при одном
и том же составе корзины, инвентаре и данных рецептов.

### FR-06. Цены и стоимость

Для предмета можно указать цену покупки у NPC. Для рецепта можно указать цену
одного запуска крафта. В MVP цена задаётся в одной валюте игры.

Сервис показывает раздельно:

- стоимость докупки недостающих покупаемых компонентов;
- стоимость всех необходимых операций крафта;
- общую сумму;
- позиции, для которых цена не задана.

Базовые ресурсы тоже могут иметь цену, если их можно купить или пользователь
хочет оценивать их условную стоимость. При расчёте из имеющегося инвентаря
такие ресурсы не считаются покупкой; в стоимость попадает только дефицит.

## 4. Правила расчёта

1. Все количества хранятся как неотрицательные целые числа, цены — как
   `NUMERIC`, не как `float`.
2. Рецепт с выходом `output_quantity > 1` учитывается кратно запускам:
   необходимое число запусков округляется вверх.
3. Сначала система покрывает потребность остатками из общего инвентаря.
4. Оставшаяся потребность в крафтовом предмете преобразуется в его
   ингредиенты; базовый или покупаемый предмет становится листом дерева.
5. При расчёте максимума сервис подбирает наибольшее целое количество, для
   которого дерево можно покрыть текущими запасами без докупки.
6. Нельзя молча подменять предметы другого грейда или другого `item_id`.

## 5. Рекомендуемая база данных

Для развёрнутого веб-сервиса рекомендуется **PostgreSQL**. Задача имеет
выраженные связи «предмет — рецепт — ингредиент», требует внешних ключей,
транзакционной записи рецепта и в будущем может получить пользователей,
админов и Telegram-аккаунты. PostgreSQL хорошо подходит для этого с самого
начала.

SQLite остаётся хорошим вариантом только для локального однопользовательского
прототипа. Если сервис планируется публиковать и развивать, миграция с SQLite
позже добавит лишнюю работу.

### Минимальная схема

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `items` | `id`, `code`, `name`, `grade`, `kind`, `category`, `is_active` | Единый каталог ресурсов и результатов крафта. |
| `recipes` | `id`, `output_item_id`, `output_quantity`, `craft_cost`, `is_active` | Описание одного запуска рецепта. |
| `recipe_ingredients` | `recipe_id`, `item_id`, `quantity` | Состав рецепта. Уникальность: один предмет один раз в рецепте. |
| `item_prices` | `id`, `item_id`, `source`, `amount`, `currency`, `is_active` | Цена предмета, в MVP источник `npc` или `manual`. |
| `users` *(позже)* | `id`, `display_name`, `role`, `created_at` | Учётные записи и роли. |
| `telegram_accounts` *(позже)* | `user_id`, `telegram_id`, `username` | Связь аккаунта с Telegram. |

Рекомендуемые ограничения: `items.code` уникален, количества строго больше
нуля, `recipes.output_item_id` ссылается на `items`, `recipe_ingredients`
ссылается на существующие рецепт и предмет. Рецепт и его ингредиенты нужно
сохранять одной транзакцией.

В первой версии пользовательский `inventory` и `basket` не обязательны в БД:
они передаются в тело запроса и сохраняются в `localStorage` браузера. Это
делает гостевой сценарий простым. После появления аккаунтов их можно добавить
в таблицы `inventories`, `inventory_items`, `craft_baskets`,
`craft_basket_items`.

## 6. Черновой HTTP API

### Пользовательские методы

```text
GET  /api/v1/items?category=&grade=
GET  /api/v1/items/{item_id}
GET  /api/v1/recipes/{recipe_id}
POST /api/v1/calculations/tree
POST /api/v1/calculations/capacity
POST /api/v1/calculations/basket
```

`POST /calculations/tree` принимает `recipe_id` и желаемое количество.
`POST /calculations/capacity` — рецепт и список запасов. `POST
/calculations/basket` — массив целей и единый инвентарь. Пример общей формы:

```json
{
  "basket": [{"recipe_id": "…", "quantity": 3}],
  "inventory": [{"item_id": "…", "quantity": 20}]
}
```

Ответ корзины включает дерево для каждой цели и общую сводку: `required`,
`stock_used`, `craft_steps`, `missing`, `cost_breakdown`, `total_cost` и
`unpriced_items`.

### Административные методы

```text
POST  /api/v1/admin/items
PATCH /api/v1/admin/items/{item_id}
POST  /api/v1/admin/recipes
PATCH /api/v1/admin/recipes/{recipe_id}
PUT   /api/v1/admin/recipes/{recipe_id}/ingredients
PUT   /api/v1/admin/items/{item_id}/prices/{source}
```

Изменение ингредиентов через `PUT` заменяет полный состав рецепта и выполняет
валидацию графа до фиксации транзакции.

## 7. Интерфейс

Для MVP достаточно одного веб-интерфейса с четырьмя представлениями:

1. **Каталог и рецепт** — фильтры по категории и грейду, карточка рецепта,
   разворачиваемое дерево и плоская сводка.
2. **Мои запасы** — таблица «предмет — грейд — есть», сохранённая в браузере.
3. **Корзина крафта** — цели крафта, общий инвентарь и результат расчёта.
4. **Администрирование** — формы предметов, рецептов, ингредиентов и цен.

На экране расчёта лучше показывать дерево и итоговую таблицу одновременно:
дерево объясняет происхождение потребностей, а таблица удобна для подготовки
ресурсов. В узле дерева стоит явно маркировать: «есть в запасе», «надо
скрафтить», «надо купить у NPC» и «цена не задана».

Для фронтенда подойдёт Svelte: у него достаточно простой вход, а состояние
дерева, запасов и корзины будет заметно удобнее, чем в разрозненном vanilla
JavaScript. Если цель — быстрее освоить Rust-бэкенд, первую версию можно
сделать серверными HTML-шаблонами и небольшим JavaScript, затем вынести UI в
Svelte без изменения расчётного API.

## 8. Авторизация и регистрация

Регистрация обычных пользователей в MVP не нужна. Гость хранит инвентарь и
корзину в браузере, а расчётный API не требует входа.

Административные маршруты нельзя оставлять открытыми. Минимальный вариант для
MVP — один секретный админ-токен в переменной окружения и заголовок
`Authorization: Bearer …`. Это годится только для личного закрытого сервиса.

Следующий этап — авторизация через Telegram:

1. бот или Telegram Login подтверждает Telegram ID;
2. сервер создаёт/находит запись `users` и связанную `telegram_accounts`;
3. роль `admin` выдаётся вручную списку доверенных Telegram ID;
4. инвентарь и корзины можно синхронизировать между устройствами.

Таким образом, полноценная регистрация с паролями не потребуется: Telegram
будет поставщиком идентичности, а сервис — хранителем ролей и игровых данных.

## 9. Технический контур и порядок работы

- Backend: Rust, Tokio, Axum, SQLx, PostgreSQL.
- Расчётный модуль должен быть отдельной библиотекой без HTTP и БД: он получает
  граф рецептов, инвентарь и корзину, а возвращает структурированный результат.
- Для расчётного модуля сначала пишутся unit-тесты: простая цепочка, общий
  компонент в двух ветках, использование составного предмета из запаса,
  несколько целей корзины, выход рецепта больше единицы, разные грейды, цикл.
- HTTP-слой и UI не должны содержать собственную логику разложения рецептов.

Первый практический milestone: создать миграции `items` / `recipes` /
`recipe_ingredients`, описать маленькими тестами разложение одного рецепта до
базовых компонентов и только потом добавлять API и интерфейс.

## 10. Открытые решения

Перед началом реализации нужно подтвердить:

1. Цена базового ресурса — это всегда NPC-цена, ручная оценка или оба варианта?
2. Нужны ли несколько валют или достаточно одной?
3. Может ли один и тот же предмет иметь несколько альтернативных рецептов?
4. Должна ли система сама выбирать выгодный путь из «скрафтить / купить», если
   известны обе цены, или в MVP она только показывает оба значения?
5. Категории и грейды задаются свободно администратором или ограничиваются
   фиксированным игровым справочником?
