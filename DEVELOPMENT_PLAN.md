# План Разработки ECS Rust Engine

Этот проект разрабатывается как учебная ECS-библиотека через TDD.

План специально разбит на маленькие, достижимые этапы. Каждый новый этап начинается с тестов, которые описывают желаемое поведение. Реализация начинается только после того, как ожидаемое поведение стало понятным.

## Цель Первого Milestone

Собрать маленькую ECS-библиотеку, вдохновленную Bevy и Legion.

Первый завершенный milestone должен поддерживать:

- создание сущностей
- привязку компонентов к сущностям
- чтение и изменение компонентов
- поиск сущностей по наборам компонентов
- запуск систем
- запуск систем через schedule

## Этап 0: Структура Библиотеки

Цель: убедиться, что проект организован как library crate.

Ожидаемый результат:

- публичный API экспортируется из корня библиотеки
- интеграционные тесты могут импортировать crate
- examples могут использовать crate так же, как внешний пользователь

TDD-фокус:

- проверить, что интеграционный тест может импортировать crate

## Этап 1: Entity

Цель: ввести тип идентификатора сущности.

Ожидаемое поведение:

- сущность можно копировать
- сущности можно сравнивать
- сущности можно использовать как ключи в map или set
- сущности с одинаковым идентификатором равны
- сущности с разными идентификаторами не равны

TDD-фокус:

- равенство
- неравенство
- поведение при использовании как ключа

## Этап 2: World Создает Entity

Цель: ввести world как владельца выделения сущностей.

Ожидаемое поведение:

- можно создать новый world
- spawn создает новую сущность
- повторные spawn создают разные сущности

TDD-фокус:

- создание world
- создание сущности
- уникальность созданных сущностей

## Этап 3: Хранилище Компонентов

Цель: хранить компоненты одного конкретного типа.

Ожидаемое поведение:

- компонент можно вставить для сущности
- компонент можно прочитать для сущности
- компонент можно получить для изменения
- компонент можно удалить у сущности
- отсутствие компонента возвращает пустой результат, а не ошибку выполнения

TDD-фокус:

- вставка и чтение
- поиск отсутствующего компонента
- mutable-доступ
- удаление

## Этап 4: World Хранит Несколько Типов Компонентов

Цель: позволить world владеть хранилищами компонентов разных типов.

Ожидаемое поведение:

- компонент поддерживаемого типа можно вставить в world
- компонент можно получить обратно по его конкретному типу
- разные типы компонентов не конфликтуют
- поиск отсутствующего типа компонента возвращает пустой результат

TDD-фокус:

- вставка и чтение через world
- хранение двух разных типов компонентов
- поиск отсутствующего типа

## Этап 5: Mutable-Доступ К Компонентам Через World

Цель: позволить изменять компоненты через world.

Ожидаемое поведение:

- mutable-ссылку на компонент можно запросить через world
- изменения через mutable-доступ сохраняются
- отсутствующий mutable-доступ возвращает пустой результат

TDD-фокус:

- mutable-поиск
- сохранение изменений
- поиск отсутствующего компонента для изменения

## Этап 6: Bundles И Spawn С Компонентами

Цель: создавать сущности сразу с начальными компонентами.

Ожидаемое поведение:

- сущность можно создать с одним компонентом
- сущность можно создать с несколькими компонентами
- все компоненты из bundle привязываются к новой сущности

TDD-фокус:

- spawn с bundle из одного компонента
- spawn с bundle из двух компонентов
- проверка, что все вставленные компоненты доступны после создания

## Этап 7: Query Одного Компонента

Цель: находить все сущности с конкретным типом компонента.

Ожидаемое поведение:

- query возвращает только сущности с запрошенным компонентом
- query предоставляет сущность и ссылку на компонент
- сущности без запрошенного компонента пропускаются

TDD-фокус:

- количество результатов query
- содержимое результатов query
- пропуск неподходящих сущностей

## Этап 8: Query Двух Компонентов

Цель: находить сущности, у которых одновременно есть два конкретных типа компонентов.

Ожидаемое поведение:

- query возвращает только сущности с обоими запрошенными компонентами
- query предоставляет сущность и ссылки на оба компонента
- сущности только с одним из запрошенных компонентов пропускаются

TDD-фокус:

- пересечение наборов компонентов
- содержимое результатов query
- пропуск частичных совпадений

## Этап 9: Mutable Query Для Systems

Цель: поддержать первый полезный system-style query.

Ожидаемое поведение:

- query может предоставить mutable-доступ к одному типу компонента
- query может одновременно предоставить shared-доступ к другому типу компонента
- изменения во время итерации сохраняются
- сущности без любого из нужных компонентов пропускаются

TDD-фокус:

- изменение через query
- чтение другого компонента во время изменения
- пропуск неполных сущностей

## Этап 10: Systems

Цель: представить логику как systems, которые работают с world.

Ожидаемое поведение:

- system может получить mutable-доступ к world
- system может использовать query для обновления компонентов
- вызов system меняет состояние world ожидаемым образом

TDD-фокус:

- одна system меняет один компонент
- system в стиле movement читает один компонент и изменяет другой

## Этап 11: Schedule

Цель: запускать несколько systems в контролируемом порядке.

Ожидаемое поведение:

- systems можно добавить в schedule
- запуск schedule выполняет все systems
- systems выполняются в порядке добавления
- изменения состояния от ранних systems видны более поздним systems

TDD-фокус:

- одна system в schedule
- несколько systems в schedule
- порядок выполнения

## Этап 12: Первый Example

Цель: создать первый пользовательский пример библиотеки.

Ожидаемое поведение:

- example создает world
- example создает сущности с компонентами
- example запускает system или schedule
- example демонстрирует видимое изменение состояния

TDD-фокус:

- основное поведение остается покрытым тестами
- example используется для обучения и ручной проверки

## Рабочее Правило

Не переходить к следующему этапу, пока текущий этап не имеет:

- тестов, описывающих поведение
- проходящей реализации
- короткого разбора того, что было изучено
- нерешенных дизайн-вопросов, которые блокируют следующий этап
